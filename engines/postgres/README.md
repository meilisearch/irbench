# Postgres

Image: `pgvector/pgvector:0.8.7-pg17` (Postgres 17 + pgvector 0.8, host port 15432, database `irbench`). Adapter: `adapter.py`, built on the shared `irbench.engines.postgres.PostgresAdapter`.

## What the default track sends

| Scenario requirement | Postgres setting |
|---|---|
| Searchable fields | `text` columns plus one generated, stored `tsv tsvector` combining them with `setweight` in scenario order: `name` A, `product_class` B, `category` C, `features` D, `description` D (Postgres has four weight classes for five fields). GIN index on `tsv` |
| Synonyms | `synonyms.txt` as a `thesaurus` dictionary (`tsearch/irbench_ecommerce_product_search.ths`, generated by `adapter.thesaurus_file()`, mounted read-only) with `Dictionary = english_stem`, placed before `english_stem` for every word token type (`asciiword`, `word`, and the hyphenated `asciihword`, `hword`, `hword_asciipart`, `hword_part`). Each member maps to the group's first member and both sides pass through the stemmer, so `kids`/`children`, `tv`/`television`, `microfiber`/`microfibre` meet on one lexeme (a plain `synonym` dictionary emits its substitute unstemmed, which only unified `gray`/`grey`, `color`/`colour`, `tub`/`bathtub`). **Dropped:** the groups `three seater, 3 seater` and `two drawer, 2 drawer`: they contain digit tokens, and `websearch_to_tsquery` does not apply multi-word thesaurus phrases on the query side, so documents would be indexed as `three seater` while the query `3 seater` stayed `3 & seater` and matched nothing |
| Filterable / facet text fields | `<field>__terms text[]` with a GIN index |
| Numeric filterable / sortable fields | `double precision` columns with a B-tree index |
| Shared vectors | `embedding vector(dim)`, HNSW `vector_cosine_ops` at pgvector's defaults (`m = 16`, `ef_construction = 64`) |
| Document loading | `COPY ... FROM STDIN`, 2000 rows per batch; indexes are built after the load, then `ANALYZE` |
| `hnsw.ef_search = 100`, `hnsw.iterative_scan = relaxed_order` | set per database (and in the loading session); each carries a `justification:` in the config (`ef_search = 100` is the smallest value that returns `top_k` rows from one scan without relying on iterative scans; the other engines' pools differ: the Elasticsearch adapter sets only `k` = the request depth (100 for relevance, the page size for speed), so `num_candidates` defaults to 1.5 × k: 150 at 100, 30 at 20, and the Qdrant adapter sets no `ef`, so it defaults to the collection's `ef_construct` of 100; build parameters differ too: HNSW `m` is 16 for all, `ef_construction` is 64 in pgvector against 100 in Elasticsearch and Qdrant; iterative scans let filtered vector queries keep scanning until `top_k` rows pass the filter) |

## What the tuned track changes

Found by a sweep scored on nDCG@10 per scenario and base; each value is justified in `configs/<scenario>.yaml`.

- keyword, every scenario: `match: any`, the words of `websearch_to_tsquery` OR-ed instead of AND-ed (same parsing, stemming and thesaurus): `replace(websearch_to_tsquery(...)::text, ' & ', ' | ')::tsquery`. On web-questions also `normalization: 1` (`ts_rank` divided by 1 + log(document length)). Every matching document is ranked, so keyword requests are slower than with AND.
- hybrid: on WANDS, OR matching with the keyword side weighted 2x in the RRF; on the knowledge-base scenarios, AND matching with the vector side weighted 2x. Weights scale each side's `1 / (60 + rank)` inside the same SQL statement.

Config keys (`search.<base>`): `match` (`all` | `any`), `rank` (`ts_rank` | `ts_rank_cd`), `normalization` (the rank functions' integer flags) and `rrf` (`{k, weights: [keyword, vector]}`, hybrid). Any other key is refused.

## Languages

The non-English scenarios (Japanese, Spanish and Chinese) set the language in the config's `default` block. Each setting has a `justification:` entry.

| Scenario | default track | tuned track |
|---|---|---|
| Japanese | `index.text_search_config: simple`. Postgres has no Japanese configuration, so a Japanese phrase with no spaces stays one token | may use PGroonga (`index.text_search: pgroonga` with `compose: compose.pgroonga.yaml`, justified). It is kept only if it wins on nDCG@10 |
| Spanish | `index.text_search_config: spanish`, the built-in configuration | no plugin; usual sweep |
| Chinese (`ecommerce/title-search-zh`, `media/video-search-zh`) | `index.text_search_config: simple`. Postgres has no Chinese configuration, so an unspaced title stays one token and keyword search finds little | may use `compose: compose.zh.yaml`: PGroonga (`index.text_search: pgroonga`, `index.pgroonga_tokenizer: TokenBigram` or `TokenNgram`) or zhparser (`index.text_search_config: zhparser`). A variant replaces `simple` only if significantly better |

`index.text_search_config` names the built-in configuration that the scenario's configuration is copied from. With no key, it is `english`, as before. The stemmer in the thesaurus dictionary follows it (`spanish_stem` for `spanish`); a configuration with no built-in stemmer, such as `simple`, uses the `simple` dictionary.

### PGroonga (tuned Japanese track)

`docker/Dockerfile.pgroonga` builds on the same `pgvector/pgvector:0.8.7-pg17` image as `compose.yaml` (pgvector is its official `postgresql-17-pgvector` package) and installs `postgresql-17-pgdg-pgroonga=4.0.6-1` from PGroonga's official apt repository (`packages.groonga.org`, the `groonga-apt-source` package for Debian bookworm). `docker/compose.pgroonga.yaml` is `compose.yaml` with `build:` and the local tag `irbench-postgres-pgroonga:0.8.7-pg17`; ports, healthcheck and volumes are the same.

`index.text_search` is `tsvector` (default) or `pgroonga`. With `pgroonga` there is no `tsv` column and no text search configuration; the text index is `USING pgroonga ((ARRAY[<searchable columns>]))`, and the keyword predicate is `ARRAY[<columns>] &@~ pgroonga_condition($1, weights => ARRAY[5,4,3,2,1], index_name => ...)`, scored by `pgroonga_score(tableoid, ctid)`. The weights are the scenario's field boosts. `&@~` is PGroonga's query syntax: every word is required, as with `websearch_to_tsquery`. The default tokenizer (`TokenBigram`) is used. `search.keyword.match: any`, `rank` and `normalization` are tsvector features and are rejected with PGroonga; the synonym thesaurus is not loaded either. PGroonga only scores rows reached through its index, so the planner must use the index; on a 20,000-row probe table it chose a bitmap index scan and the scores were non-zero, whereas a sequential scan scores every row 0.

### zhparser and PGroonga (tuned Chinese track)

`docker/Dockerfile.zh` builds on the same `pgvector/pgvector:0.8.7-pg17` image. It installs PGroonga as `Dockerfile.pgroonga` does, then builds SCWS (`hightman/scws`) and zhparser (`amutu/zhparser`) unmodified from pinned upstream commits, since neither has a PGDG package; SCWS's shipped dictionary is used. `docker/compose.zh.yaml` is `compose.yaml` with `build:` and the local tag `irbench-postgres-zh:0.8.7-pg17`.

`index.text_search_config: zhparser` creates the extension and a configuration on zhparser's parser (`PARSER = zhparser`) instead of copying a built-in one, and maps its content token types `n,v,a,i,e,l` (noun, verb, adjective, idiom, exclamation, temporary word) to `simple`, as zhparser's README configures it. It takes no thesaurus: a scenario with synonyms must declare a `synonyms:` reason. `index.pgroonga_tokenizer` (`TokenBigram`, PGroonga's default, or `TokenNgram`) adds `WITH (tokenizer='...')` to the PGroonga index.

`search.keyword.query: plain` builds the tsquery with `plainto_tsquery` instead of `websearch_to_tsquery` (both documented Postgres functions). It matters for zhparser: `websearch_to_tsquery` reads an unspaced query that the parser splits into several words as a phrase (`'宝宝' <-> '护' <-> '肚'`: adjacent and in order), while `plainto_tsquery` joins the words with `&` (and `match: any` turns that into `|`).

## Modes

Every mode is one SQL statement. Placeholders are `$n::text` plus a cast; the query text is always a parameter.

- keyword: `tsv @@ websearch_to_tsquery(<config>, $1::text)`, ranked by `ts_rank`, ties by `id`. AND semantics (Postgres as shipped); no typo or prefix tolerance.
- semantic: `ORDER BY embedding <=> $1::text::vector` (cosine distance) with the HNSW index.
- hybrid: reciprocal rank fusion, k = 60, in one statement: the keyword top `depth` and the vector top `depth` (`depth` is the request depth: `top_k` = 100 for relevance, the page size for speed) (each with the filter) are numbered with `row_number()`, combined by `FULL OUTER JOIN`, scored `1/(60 + r)` per side. Plain hybrid returns ids straight from the fused CTEs; only the sorted and faceted shapes join back to the table for the sort column or `__terms`.
- filtered: `<field>__terms @> ARRAY[$n::text]` for `eq`, `<field> >= / <= $n::text::float8` for ranges; applied inside both sides of hybrid.
- sorted: the keyword base sorts every match, the semantic base sorts the `depth` nearest (`top_k` for relevance, the page size for speed); `ORDER BY <field> <dir> NULLS LAST, id`.
- faceted: one statement returns one row `{ids, facets}`. Counts are `unnest(<field>__terms)` grouped over the query's own match set, at most `max_facet_values` buckets per facet, most frequent first with ties by value (keyword: every match; semantic: every document passing the filter, counted with no ordering or limit so an HNSW scan can never truncate them; hybrid: the fused set); `ids` is the top `limit` of that set, taken from a separate ranked subquery on the semantic base. Intermediate sets project only `id`, `score`, and the sort or `__terms` columns, never the embedding or text columns.
- The facet verification fetch (`facets=False`) is the plain query with a larger limit.

## Known limits

- Four weight classes for five fields: `features` and `description` share class D.
- `websearch_to_tsquery` requires every term (AND), so long natural-language queries match fewer documents than with OR-style engines; there is no typo or prefix tolerance.
- `ts_rank` is not BM25 (no IDF); it uses term frequency and the weights.
- Faceted on the semantic base scans every filtered document (the spec's definition of the match set); the performance numbers show its cost.
- Digit synonym groups are not loaded (see Synonyms).
- Hybrid fusion over `depth` per side can return fewer than `limit` documents if the sides overlap heavily.

## Changing this configuration

Edit `configs/ecommerce/product-search.yaml` (`index.settings` are database-level GUCs). If `synonyms.txt` changes, regenerate `docker/tsearch/irbench_ecommerce_product_search.ths` from `adapter.thesaurus_file()`; `test_thesaurus_file_matches_scenario_synonyms` prints the expected content. Run `uv run pytest -m docker -k postgres` before opening a PR.
