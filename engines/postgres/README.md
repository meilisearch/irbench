# Postgres

Image: `pgvector/pgvector:0.8.7-pg17` (Postgres 17 + pgvector 0.8, host port 15432, database `irbench`). Adapter: `adapter.py`, built on the shared `irbench.engines.postgres.PostgresAdapter`.

## What the default track sends

| Scenario requirement | Postgres setting |
|---|---|
| Searchable fields | `text` columns plus one generated, stored `tsv tsvector` combining them with `setweight` in scenario order: `name` A, `product_class` B, `category` C, `features` D, `description` D (Postgres has four weight classes for five fields). GIN index on `tsv` |
| Synonyms | `synonyms.txt` as a synonym dictionary (`tsearch/irbench_ecommerce_product_search.syn`, generated by `adapter.synonym_file()`, mounted read-only), chained before `english_stem` in a text search configuration copied from `english`. Multi-word groups (`three seater, 3 seater` and `two drawer, 2 drawer`) are dropped: a synonym dictionary maps single tokens |
| Filterable / facet text fields | `<field>__terms text[]` with a GIN index |
| Numeric filterable / sortable fields | `double precision` columns with a B-tree index |
| Shared vectors | `embedding vector(dim)`, HNSW `vector_cosine_ops` at pgvector's defaults (`m = 16`, `ef_construction = 64`) |
| Document loading | `COPY ... FROM STDIN`, 2000 rows per batch; indexes are built after the load, then `ANALYZE` |
| `hnsw.ef_search = 100`, `hnsw.iterative_scan = relaxed_order` | set per database (and in the loading session); each carries a `justification:` in the config (default `ef_search` 40 could not return `top_k = 100`; iterative scans let filtered vector queries still fill `top_k`) |

## Modes

Every mode is one SQL statement. Placeholders are `$n::text` plus a cast; the query text is always a parameter.

- keyword: `tsv @@ websearch_to_tsquery(<config>, $1::text)`, ranked by `ts_rank`, ties by `id`. AND semantics (Postgres as shipped); no typo or prefix tolerance.
- semantic: `ORDER BY embedding <=> $1::text::vector` (cosine distance) with the HNSW index.
- hybrid: reciprocal rank fusion, k = 60, in one statement: the keyword top `top_k` and the vector top `top_k` (each with the filter) are numbered with `row_number()`, combined by `FULL OUTER JOIN`, scored `1/(60 + r)` per side, and joined back to the table.
- filtered: `<field>__terms @> ARRAY[$n::text]` for `eq`, `<field> >= / <= $n::text::float8` for ranges; applied inside both sides of hybrid.
- sorted: the keyword base sorts every match, the semantic base sorts the `top_k` nearest; `ORDER BY <field> <dir> NULLS LAST, id`.
- faceted: one statement returns one row `{ids, facets}`. Counts are `unnest(<field>__terms)` grouped over the query's own match set (keyword: every match; semantic: every document passing the filter); `ids` is the top `limit` of that set.
- The facet verification fetch (`facets=False`) is the plain query with a larger limit.

## Known limits

- Four weight classes for five fields: `features` and `description` share class D.
- `websearch_to_tsquery` requires every term (AND), so long natural-language queries match fewer documents than with OR-style engines; there is no typo or prefix tolerance.
- `ts_rank` is not BM25 (no IDF); it uses term frequency and the weights.
- Faceted on the semantic base scans every filtered document (the spec's definition of the match set); the performance numbers show its cost.
- Hybrid fusion over `top_k` per side can return fewer than `limit` documents if the sides overlap heavily.

## Changing this configuration

Edit `configs/ecommerce/product-search.yaml` (`index.settings` are database-level GUCs). If `synonyms.txt` changes, regenerate `docker/tsearch/irbench_ecommerce_product_search.syn` from `adapter.synonym_file()`; `test_synonym_file_matches_scenario_synonyms` prints the expected content. Run `uv run pytest -m docker -k postgres` before opening a PR.
